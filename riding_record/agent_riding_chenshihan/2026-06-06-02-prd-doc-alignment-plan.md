# 2026-06-06 计划摘抄 02：ARY PRD 文档对齐计划

来源：

- `docs/superpowers/plans/2026-06-06-ary-prd-doc-alignment.md`

类型：

- 文档对齐实施计划

目标：

- 维护一组面向后续开发者/Agent 的文档，强制未来工作从 `PRD.md` 出发，而不是从旧 PoC 假设或次级文档出发。

总体思路：

- 不直接改 `PRD.md`
- 在 `PRD.md` 之外补一层面向实现者的上下文设计与执行计划
- 用这两份文档约束未来工作如何读代码、如何表述差异、如何避免过度承诺

计划分成三块：

## 1. 维护一份稳定的 PRD 上下文设计

重点内容：

- 明确阅读顺序
- 明确当前代码和 PRD 的关键差异
- 明确未来讨论数据边界时的表达要求

要求明确写出的现实差异：

- localStorage vs SQLite
- PRD Runner API vs 当前真实接口
- 榜单刷新未自动化
- Harness 仍是派生逻辑
- ARY 仍会保留最佳归档原文

## 2. 维护一份 PRD 对齐的执行计划

重点内容：

- 所有未来实现工作要以当前代码真实状态为起点，而不是按假想重写
- 显式检查真实提交生命周期：
  - 提交先写入
  - artifact 在评分后被清空
  - 最佳结果保留在 `TeamArchive`
- 明确禁止未来文档过度承诺：
  - 不要把榜单说成已经自动调度
  - 不要把 Harness 说成独立流水线
  - 不要把 ARY 说成完全零原文保留

## 3. 让这套文档成为默认入口

要求：

- Agent 不应先看 `README.md` / `ROADMAP.md`
- 面向公开的仓库文档应视为次级说明
- 只有用户明确要求，或实现与公开说明发生漂移时，才优先更新公共文档

这个计划最重要的价值：

- 后续工作不再从旧的“假前端 PoC”叙事出发
- 隐私边界、实际实现、公开表述三者保持一致
