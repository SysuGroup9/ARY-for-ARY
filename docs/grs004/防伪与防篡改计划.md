## 1. 更新背景

GRS003 版本的《防伪与防篡改安全计划》已经完成过一次从旧 `team / submission / runner` 思路到 GRS003 `Registration / RaceProject / CAConnection / Evidence / Projection` 语义的调整。

进入 GRS004 后，项目状态又发生了变化：

- 公开端、赛事控制台、管理控制台、大屏控制台已经分层。
- `User.roles` 多角色体系已经成为访问控制基础。
- GitHub OAuth 主链路已经具备，但本地演示账号仍保留。
- `Registration`、`RaceProject`、`CAConnection`、`Session`、`Evidence`、`Projection`、`Work`、`JudgeAssignment`、`JudgingRecord`、`Award`、`Report` 等 GRS003 核心模型已经落入 `prisma/schema.prisma`。
- CA 接入已经具备 handshake、signal push、snapshot fetch 的最小运行时桥。
- Projection 已用于 Live Hall / 大屏 / Race Console 的过程展示。
- Runner 已从核心裁决链路降级为辅助处理或兼容链路，不能再作为防伪防篡改设计的中心。

因此，GRS004 的安全计划不再把重点放在“设计一套未来安全系统”，而是要围绕当前已经存在的模型和服务，明确：

1. 当前哪些安全边界已经具备；
2. 哪些仍只是计划，没有实现；
3. 下一步应该优先补哪些字段、校验和审计链路；
4. 哪些 GRS003 旧表述已经不适合继续作为项目说明。

## 2. GRS004 安全目标

GRS004 阶段的防伪与防篡改目标是：

1. **保证身份边界可信**  
   后台访问必须基于登录态和 `User.roles`，并结合资源归属进行判断。

2. **保证 CA 接入来源可信**  
   只有已登记、已握手、未禁用、且归属正确的 `CAConnection` 可以写入有效 Session、Evidence 和 Projection。

3. **保证过程数据可追溯**  
   CA signal、snapshot fetch、Session、Evidence、Projection 之间必须保留来源引用和时间线。

4. **保证作品与材料完整性可补证**  
   Work、代码材料、GitHub Repo、Demo 附件、题目包和评测配置需要逐步补齐 hash / sourceRef / version / actor 等完整性元数据。

5. **保证公开展示不直接消费原始不可信输入**  
   Public Site、Live Hall、Screen Console、Jumbotron 读取 Projection、Evidence 摘要、公开 Work、已发布 Award / Report，而不是直接读取原始 CA Session。

6. **风险提示优先于自动处罚**  
   接入失败、无 CA 数据、证据缺口、疑似重放、材料完整性缺口，默认形成 review flag / readiness / integrity gap，不自动取消资格。

## 3. 当前已具备的安全能力

### 3.1 身份与角色边界

当前项目已经具备：

- `User.rolesJson` 表达多角色。
- `profileCompleted`、`githubAccount` 等字段支撑 GitHub OAuth 和资料补全方向。
- Console 入口按 `RIDER`、`ORGANIZER`、`JUDGE`、`ADMIN` 做访问控制。
- Organizer、Rider、Judge 视图均按赛事和资源归属过滤。
- Admin Console 用于系统级用户与角色维护。

仍需注意：

- 本地用户名 / 密码演示账号仍存在，不应在文档中描述为最终生产身份入口。
- GitHub OAuth 已具备主链路，但仍需要继续完善错误提示、profile completion 和角色授权流程。

### 3.2 CAConnection 登记与握手

当前已具备：

- `CAConnection` 模型保存：
  - `raceProjectId`
  - `caType`
  - `connectorId`
  - `connectorSecret`
  - `connectorBaseUrl`
  - `connectorVersion`
  - `caProjectId`
  - `ingestionStatus`
  - `handshakeCompletedAt`
  - `disabledAt`
  - `lastSyncedAt`
- `completeCAConnectionHandshake()` 会校验：
  - connection 是否存在；
  - `connectorSecret` 是否匹配；
  - `connectorId`、`caProjectId` 是否匹配；
  - connection 是否被禁用；
  - 通过后写入 `handshakeCompletedAt` 和 `ingestionStatus`。

这意味着 GRS004 的可信 CA 边界已经不是空白：未登记、secret 不匹配、scope 不匹配、disabled 的 connector 不会通过握手。

### 3.3 Riding Signal 接入校验

当前 `ingestRidingSignalMessage()` 已具备：

- zod schema 校验 signal 结构。
- 校验 `authToken` 与 `connectorSecret`。
- 校验 `handshakeCompletedAt`，未握手连接不能写入有效事件。
- 校验 connection 未被禁用。
- 校验以下 scope 一致：
  - `raceProjectId`
  - `registrationId`
  - `raceId`
  - `caProjectId`
  - `connectorId`
- 通过 `idempotencyKey` 对 `CAIngestionEvent` 做去重。
- 写入 `CAIngestionEvent.payloadJson` 保留原始接入事件。
- 根据 signal upsert `Session`。
- 更新 `CAConnection.ingestionStatus` 与 `RaceProject.aggregateIngestionStatus`。
- 接入后重建 `Evidence` 和 `Projection`。

这已经覆盖了 GRS003 文档里最关键的“先校验归属，再接收数据”。

### 3.4 Snapshot Fetch 边界

当前 `fetchCASessionSnapshotForConnection()` 已具备：

- 必须找到对应 `CAConnection`。
- 未握手或已禁用的 connection 不能 fetch snapshot。
- 必须存在 `connectorBaseUrl`。
- 使用 `Authorization: Bearer ${connectorSecret}` 抓取 connector snapshot。
- zod 校验 snapshot schema。
- 校验返回 payload 中的：
  - `caConnectionId`
  - `caProjectId`
  - `caSessionId`
- 通过 `snapshotFetchedAt` 判断 stale snapshot，不覆盖更新数据。
- upsert `Session` 并更新 connection / aggregate status。

因此，Snapshot fetch 不再是任意 URL 抓取，而是绑定到已登记 CAConnection 的受控拉取。

### 3.5 Evidence 与 Projection 链路

当前已具备：

- `Evidence` 模型有：
  - `registrationId`
  - `type`
  - `title`
  - `summary`
  - `sourceRefJson`
  - `visibility`
- `rebuildSessionSummaryEvidenceForRace()` 会基于 Session 重建 `SESSION_SUMMARY` Evidence。
- `Projection` 模型有：
  - `raceId`
  - `type`
  - `payloadJson`
  - `asOfAt`
- `rebuildRaceProcessProjections()` 会生成：
  - `RACE_PROGRESS`
  - `REGISTRATION_STATUS`
  - `COST`
  - `RISK`
  - `CURRENT_LEADERBOARD`
  - `EVENT_STREAM_READ_MODEL`
  - `SCREEN_FEED`
- Live Hall、大屏、Race Console 可以读取 Projection，而不是直接读取原始 CA 输入。

这说明公开展示层已经具备“读取投影，不读原始输入”的基础结构。

## 4. GRS003 旧计划中不再适合继续使用的表述

以下旧表述在 GRS004 中应废弃或改写。

### 4.1 不再以 Runner 为防伪中心

旧计划中强调 Runner 拉取提交、校验提交 hash、Runner 输出辅助评测。进入 GRS004 后，Runner 不能作为主安全链路中心。

当前应表述为：

- Runner 是兼容链路或辅助处理组件。
- 正式过程数据主链路是 CAConnection → Session → Evidence / Projection。
- Runner 若保留，必须消费已经有来源引用和完整性元数据的 Work / Evidence，而不是直接作为事实源。

### 4.2 不再把异常自动等同于 DQ

旧计划中曾强调签名失败、nonce 重放、hash mismatch 直接 DQ、大屏红色公示、排名移除。

GRS004 中应改为：

- 接入异常默认形成 `risk` / `integrity_gap` / `review readiness`。
- 是否取消资格，必须由 Organizer / Judge 依据赛事规则和证据进行人工处理。
- 大屏可以显示风险摘要，但不应默认公开完整违规细节或原始证据。

### 4.3 不再绑定具体 DCR Desktop App

旧计划中把安全入口绑定到 “DCR Desktop App 生成密钥对”。当前项目更通用，核心是 CAConnection / connector。

GRS004 中应表述为：

- 可以由 Claude Code、Codex 或其他 connector 接入。
- 安全边界是 `CAConnection` 登记、secret、scope、handshake、signal schema、snapshot fetch，而不是某一个固定客户端。
- 后续可以在 connector 层增加公钥、签名、nonce、时间窗，但不应写成“必须 DCR Desktop App”。

### 4.4 不再把 Team 当作主要安全对象

当前仍保留 `Team` 兼容旧链路，但 GRS004 文档中的主要保护对象应该是：

- `User`
- `Registration`
- `RaceProject`
- `CAConnection`
- `Session`
- `Evidence`
- `Projection`
- `Work`
- `JudgingRecord`
- `Award`
- `Report`

Team 只能作为兼容层或历史数据容器出现。

## 5. 当前主要缺口

### 5.1 缺少消息级签名

当前使用 `connectorSecret` bearer token 保护 handshake、signal、snapshot fetch，但还没有消息级签名。

缺口包括：

- 没有 `publicKey` / `credentialFingerprint` 字段。
- 没有 `signature` 字段。
- 没有对 payload body 做签名校验。
- 没有签名算法版本管理。

GRS004 后续建议：

- 在 `CAConnection` 或新增 `CACredential` 中保存 credential fingerprint。
- Signal payload 增加 `signature`、`signedAt`、`signatureVersion`。
- 服务端对 canonical JSON 或 body digest 验签。

### 5.2 幂等键已有，但防重放仍不完整

当前 `idempotencyKey` 已唯一，重复消息会 dedupe。

仍缺少：

- 时间窗校验。
- sequence 单调性校验。
- 同一 `caConnectionId + caSessionId + sequence` 唯一约束。
- 已接收消息 digest 与 idempotencyKey 冲突检测。

GRS004 后续建议：

- `CAIngestionEvent` 增加 `sequence`、`payloadDigest`、`receivedAt`、`integrityStatus`。
- 对重复 idempotencyKey 但 payloadDigest 不一致的情况标记为 `integrity_gap`。

### 5.3 Work / 题目 / 外部材料缺少 hash 元数据

当前 `Work` 只有 `demoUrl`、`repoUrl`、`videoUrl`、`techNotes`，没有完整性字段。

缺口包括：

- Work source hash。
- GitHub commit SHA / tag / release digest。
- Demo 附件 hash。
- 题目包版本号与 hash。
- 评测配置版本号与 hash。

GRS004 后续建议：

- 新增 `MaterialIntegrityRecord` 或在相关模型增加 `sourceRefJson` / `contentHash`。
- 对 Race challenge materials、Work、Evidence 引用材料统一记录 sourceRef。

### 5.4 Evidence 可信度字段不足

当前 Evidence 有 `sourceRefJson` 和 `visibility`，但还没有显式 integrity 字段。

缺口包括：

- `integrityStatus`
- `confidenceLevel`
- `sourceDigest`
- `generatedFromEventIds`
- `reviewFlagJson`

GRS004 后续建议：

- Evidence 不只保存摘要，还要保存摘要来源、生成时间、可信度和是否存在缺口。

### 5.5 Projection 重建目前偏粗粒度

当前 CA signal / snapshot fetch 后会重建全赛事 Evidence 和 Projection。

优点：实现简单，保证展示能更新。  
缺点：后续赛事规模变大后可能重复计算过多。

GRS004 后续建议：

- 保留全量 rebuild 作为 fallback。
- 增加按 registration / raceProject / projection type 的局部更新能力。
- Projection 增加 `sourceVersion` 或 `inputDigest`，用于判断是否需要重算。

### 5.6 缺少统一审计模型

当前 CAIngestionEvent 保存了 payloadJson，但系统尚未有统一 SecurityAudit / IntegrityEvent。

建议新增审计对象，记录：

- actor / connector / user
- action
- targetType / targetId
- result
- reason
- payloadDigest
- ip / userAgent（如可得）
- createdAt

## 6. GRS004 推荐实现路线

### P0：先补可信链缺口

1. 为 `CAIngestionEvent` 增加：
   - `payloadDigest`
   - `sequence`
   - `receivedAt`
   - `integrityStatus`
2. 对重复 `idempotencyKey` 但 payload digest 不一致的情况返回风险状态。
3. 对 signal timestamp 增加合理时间窗检查，但只形成风险，不默认判罚。
4. 在 Evidence 中增加可信度 / 完整性状态字段，或建立独立 `EvidenceIntegrity`。
5. 在 status 文档和 README 中明确：Runner 不是主裁决链路。

### P1：补材料完整性

1. 为 Work / Race challenge materials / GitHub repo 引用增加 sourceRef 与 hash。
2. 为 Report 生成记录输入 Evidence / Projection / Work 的版本引用。
3. 为 Award / JudgingRecord 保存参考 Evidence 的快照或引用，避免后续重建导致评审依据漂移。
4. 引入统一 SecurityAudit / IntegrityEvent。

### P2：增强 connector 认证

1. 在 connector 层引入公钥注册或 credential fingerprint。
2. Signal payload 增加签名。
3. 支持 connector secret rotation。
4. 支持 disabled / revoked connector 的审计与可视化。
5. 在 Organizer Console 中显示接入可信度和风险提示。

## 7. 展示层安全规则

### 7.1 Public Site

Public Site 只能展示：

- 公开赛事信息。
- 公开 Work。
- 已发布 Award。
- 已发布且公开可见的 Report。
- 可公开 Evidence 摘要。
- Projection 摘要。

不得展示：

- 原始 CA Session。
- connectorSecret。
- 未发布评审结果。
- 内部 Evidence。
- 未确认的安全细节。

### 7.2 Live Hall / Jumbotron / Screen Console

大屏展示可以展示：

- 进度摘要。
- 风险等级摘要。
- Session activity 摘要。
- 公开榜单或过程榜单。

不应展示：

- 原始消息全文。
- connector secret / token。
- 未确认违规细节。
- 未公开作品内容。

### 7.3 Organizer / Judge Console

Organizer / Judge 可以看到更多内部摘要，但仍默认不直接展示原始 CA Session。应该优先展示：

- Evidence 摘要。
- Integrity status。
- Review readiness。
- Risk reason。
- 缺失材料提示。

## 8. 验收标准

GRS004 防伪防篡改验收建议：

- 未登记 `CAConnection` 不能完成 handshake。
- `connectorSecret` 错误时 handshake / signal / snapshot fetch 均被拒绝。
- scope mismatch 的 signal 被拒绝，不写入 Session / Evidence / Projection。
- 未握手 connection 的 signal 被拒绝。
- disabled connection 的 signal 和 snapshot fetch 被拒绝。
- 重复 idempotencyKey 不重复写入事件。
- 重复 idempotencyKey 但 payload 不一致时能形成 integrity risk（待实现）。
- snapshot payload 中 caConnectionId / caProjectId / caSessionId 不匹配时被拒绝。
- stale snapshot 不覆盖较新的 Session。
- Evidence 能追溯到 CAConnection / Session。
- Projection 能重建，且 Public / Screen 读取 Projection 而不是原始 Session。
- Work / 题目材料 hash 能记录并在读取时校验（待实现）。
- 风险默认进入 Review Flag / Readiness，不自动 DQ。

## 9. 一句话结论

GRS004 的防伪与防篡改重点，应从 GRS003 旧文档里的“Runner + 自动 DQ + 固定客户端”转向当前项目已经形成的主链路：

```text
User / roles
→ Registration
→ RaceProject
→ CAConnection handshake
→ Riding signal / snapshot fetch
→ Session
→ Evidence
→ Projection
→ Organizer / Judge review
→ Award / Report / Public display
```

当前项目已经具备 CA 接入归属校验、secret 校验、scope 校验、idempotency 去重、Session / Evidence / Projection 重建等基础能力。GRS004 后续最重要的补强方向，是消息级签名、防重放增强、材料 hash、Evidence 可信度字段和统一审计模型。

**当前实现**：**【未实现】**
