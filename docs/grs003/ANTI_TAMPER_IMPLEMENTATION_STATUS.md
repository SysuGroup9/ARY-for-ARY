# ANTI_TAMPER_IMPLEMENTATION_STATUS

## 当前已实现的防伪/防篡改功能

1. 已有 CA 数据摄取链路。
   - `src/lib/services/ca-ingestion.ts` 已承担 CA 侧数据的拉取、入库或聚合更新职责。
   - 系统已经具备把外部 CA 运行数据转成项目内可用记录的基础能力。

2. 已有证据汇总能力。
   - `src/lib/services/evidence.ts` 已能围绕报名记录、作品或关联实体收集证据数据。
   - 说明系统不是只保存最终结果，而是已经保存了一层可回溯的证据视图。

3. 已形成“采集数据 + 证据落库”的基础防伪框架。
   - 当前实现说明系统已经不是纯手工申报模式。
   - 已经具备用 CA 运行痕迹、会话信息或相关过程数据支撑真实性判断的基础结构。

4. 已有与报名/参赛主体绑定的数据关系。
   - 从现有服务文件可以确认，证据与报名记录、参赛用户、Race Project 等对象存在关联。
   - 这为后续按人、按项目、按赛事做真实性核验提供了数据基础。

## 文档中写了但代码还没实现的部分

1. 完整的防篡改闭环还没有落地。
   - 目前能看到的是“摄取”和“证据汇总”，但还不是完整的不可抵赖链路。
   - 如果文档要求对关键证据做哈希固化、链式签名、时间戳封存或不可变存储，现阶段代码里还没有形成完整实现。

2. 独立的篡改检测机制还不完整。
   - 当前代码更像是在做数据采集和证据组织。
   - 如果文档要求自动比对原始记录与展示记录、检测异常回写、识别证据缺口或生成篡改告警，这部分还没有作为完整能力落地。

3. 对外可审计的验证流程还没有完整成型。
   - 当前已有内部服务层能力，但还缺少清晰的“验证入口”。
   - 如果文档要求管理员、评审或公众可直接查看某条结论对应的原始证据、校验摘要、时间顺序和验证状态，这部分仍不算完成。

4. 证据可信度分级与规则化判定尚未形成闭环。
   - 现有实现更偏向数据收集。
   - 如果文档中要求把证据分级、定义通过/存疑/失败规则，并以统一规则驱动结果输出，代码里还没有看到完整规则引擎级实现。

5. 明确的防伪状态展示还不完整。
   - 如果文档要求把“已验证 / 待补证 / 证据冲突 / 疑似篡改”等状态直接体现在业务界面或结果流中，当前实现基础已具备，但完整产品化状态管理还没有完成。

## 下一步需要做的

1. 为关键证据建立不可变指纹。
   - 对 CA 原始返回、关键会话摘要、证据快照生成稳定哈希。
   - 在证据入库时同时保存哈希、生成时间和来源信息。

2. 区分“原始证据”和“派生证据”。
   - 原始证据保留完整来源与快照。
   - 派生证据明确标注计算方法、来源版本和生成时间，避免后续混淆。

3. 增加篡改检测任务。
   - 定期复算关键哈希。
   - 比对当前记录与历史快照。
   - 对不一致、缺失、来源变更生成异常状态或告警。

4. 建立统一的真实性判定规则。
   - 明确哪些证据足以判定“真实”。
   - 明确哪些情况属于“证据不足”“证据冲突”“疑似篡改”。
   - 让判定结果可以被服务层直接复用，而不是散落在页面逻辑里。

5. 输出可审计视图。
   - 面向管理员或评审提供单条记录的证据链页面。
   - 展示来源、时间顺序、摘要哈希、验证结果和异常原因。

6. 把防伪状态接入业务主流程。
   - 在报名、作品、评审、展示或直播大厅相关视图中显式展示验证状态。
   - 对证据缺失或校验失败的数据限制其进入高信任结果流。

7. 补测试。
   - 增加 CA 摄取失败、重复摄取、证据变更、证据缺失、哈希不一致、来源冲突等测试用例。
   - 补齐从摄取到证据判定再到状态输出的端到端覆盖。
