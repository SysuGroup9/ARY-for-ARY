# ARY GRS 003 增补：防伪与防篡改安全计划

## 1. 背景与目标

第三周增补的核心安全要求是**防伪、防篡改**，重点解决以下问题：
1. 防止选手的恶意代码或伪造数据影响比赛公平性
2. 保障企业的题目数据在传输和存储过程中不被他人恶意篡改
3. 保障 Runner 拉取参赛者提交时，提交内容未被篡改
4. 防伪检测结果与第二周 Jumbotron 大屏联动，违规选手实时展示并取消比赛资格

确保 CA（Coding Agent）上报的消息来自真实 CA（通过 DCR Desktop App 认证），且未被伪造、篡改或重放。

## 2. 威胁模型

| 攻击类型 | 描述 | 危害 |
|----------|------|------|
| Token 作弊 | 选手伪造高 Token 消耗数据 | 排名不公平 |
| 代码伪造 | 选手提交不是自己 CA 写的代码 | 评测结果失真 |
| 消息重放 | 重复提交同一份代码或消息 | 刷分、重复计费 |
| 中间人攻击 | 拦截并修改传输中的消息 | 数据被篡改 |
| 身份伪造 | 冒充其他 CA 发送消息 | 伪造他人成绩 |
| 题目篡改 | 企业题目在传输或存储中被篡改 | 影响评测公正性 |
| 提交篡改 | Runner 拉取过程中参赛者提交被篡改 | 评分结果失真 |

## 3. 安全目标

- 来源认证：确保消息确实来自真实的 CA
- 完整性保护：确保消息、题目数据在传输和存储过程中未被篡改
- 防重放：确保同一条消息不能被重复提交
- 不可否认性：CA 不能否认自己发送的消息
- 实时威慑：违规行为即时发现并在大屏公示，取消比赛资格

## 4. 技术方案

### 4.1 选手侧防护：防止恶意代码

选手通过 DCR Desktop App 进行身份认证，每个 CA 在首次启动时生成唯一的密钥对（私钥 + 公钥），私钥存储在 DCR Desktop App 本地，公钥注册到 ARY 平台。

选手每次提交代码或消息时，都必须使用私钥对消息内容进行签名。ARY 收到消息后，用该选手注册的公钥验证签名有效性。签名无效或身份不匹配的消息将被直接拒绝，同时触发违规记录。

签名内容包含时间戳和唯一随机数（nonce）。对于**提交代码类请求**，ARY 会校验时间戳是否在服务器时间的前后 5 分钟内，超时的请求将被拒绝，以防止攻击者截获并重放旧请求。

**反馈类消息不适用此时间戳限制**，参赛者向企业反馈问题不受 5 分钟超时约束。

### 4.2 企业侧防护：防止题目篡改

企业发布题目时，ARY 对题目压缩包计算哈希值并存储。后续任何读取题目数据的请求，ARY 都会重新计算哈希并与存储值比对，确保题目内容未被篡改。

企业对题目的所有修改操作都会记录审计日志，包含修改人、时间、变更内容等信息，便于事后追溯。

题目数据在传输过程中强制使用 TLS 加密，防止中间人攻击。

### 4.3 Runner 拉取防护：防止参赛者提交被篡改

参赛者提交代码后，ARY 对代码内容计算哈希值并存储。

Runner 是部署在企业内网的评测程序，由企业自行维护。Runner 从 ARY 拉取待评测提交时，ARY 同时下发代码内容和对应的哈希值。Runner 在本地执行评测前，先对拉取的代码内容计算哈希，与 ARY 下发的哈希值进行比对。

匹配则执行评测，不匹配则终止评测并上报错误。这确保了 Runner 拿到的参赛者代码在传输过程中未被篡改。

**注意**：企业的评测代码始终存储在企业内网，ARY 不接触、不存储、不传递评测代码。Runner 本身就是企业内网的一部分，评测代码由企业在 Runner 环境中自行维护。

### 4.4 与 Jumbotron 大屏联动：违规与风险实时公示

当 ARY 检测到以下情况时，触发相应处理：

**严重违规（直接取消资格 + 大屏红色 DQ 公示）：**
- 签名验证失败 → 身份伪造，无法验证来源真实性（violationType: `signature_failed`）
- nonce 重复使用 → 重放攻击，同一消息被重复提交（violationType: `nonce_reused`）
- 代码哈希不匹配 → 提交内容在传输中被篡改（violationType: `hash_mismatch`）

**高风险（标记为黄色「高风险」标签 + 大屏提醒）：**
- 时间戳超时（>5 分钟）且同一队伍在 1 小时内累计出现 3 次及以上 → 标记为高风险，提示网络异常或可能存在可疑行为（riskType: `timestamp_frequent_timeout`）

**临时拒绝（不标记）：**
- 时间戳超时（首次或偶发，1 小时内少于 3 次）→ 拒绝本次请求，提示重新提交。可能是网络延迟导致，不记录违规，不标记风险。

违规记录包含：队伍名称、违规类型、时间戳、证据摘要。

违规记录实时推送至 Jumbotron 大屏。被取消资格的队伍：
- 立即**停止前进**
- 马身变为**红色**
- 显示 **「违规-取消资格」** 标签
- 排名面板中该队伍被标记为 **DQ（Disqualified）**

被标记为高风险（黄色）的队伍：
- 马匹显示黄色「高风险」标签
- 底部 Ticker 显示风险提醒
- 组织者可点击查看详情，判断是否需要介入

被取消资格或高风险队伍的排名处理：
- DQ 队伍**不再参与后续排名**，所有历史提交标记为无效，其他队伍排名依次递补
- 高风险队伍**继续参与排名**，但标记提醒组织者关注

## 6. API 变更

### 6.1 提交代码（带签名）

请求体包含：teamId、code、tokenUsed、timestamp、nonce、signature。

ARY 验证流程：
1. 验证签名有效性
2. 检查 nonce 是否已使用
3. 检查 timestamp 是否在 5 分钟窗口内（仅针对提交代码类请求）
4. 以上全部通过后存储提交，计算代码哈希
5. 任一验证失败 → 记录违规 → 推送 Jumbotron → 拒绝请求

### 6.2 CA 注册公钥

请求包含：teamId、publicKey、keyType。

### 6.3 Runner 拉取参赛者提交

ARY 返回参赛者代码内容 + 哈希值。Runner 执行前校验哈希。

### 6.4 企业发布/修改题目

ARY 计算文件哈希并存储，修改操作记录审计日志。

### 6.5 参赛者反馈

反馈类消息不校验时间戳，但仍需签名验证和 nonce 检查。

### 6.6 Jumbotron 违规推送

当 ARY 检测到违规或高风险时，通过 WebSocket 或 Server-Sent Events 实时推送事件到 Jumbotron 大屏。

## 7. 实现计划

- Phase 1（P0）：CA 密钥对生成、公钥注册；提交消息签名与验证
- Phase 2（P1）：防重放机制；题目完整性校验；提交哈希校验
- Phase 3（P2）：密钥轮换与吊销；审计日志；Jumbotron 违规联动

## 8. 验收标准

- CA 首次启动时生成密钥对，公钥注册到 ARY
- 每条提交消息包含有效签名，ARY 验证签名
- 相同 nonce 的重复提交被拒绝
- 提交代码类请求中，超时（>5 分钟）的消息被拒绝
- 反馈类消息不受 5 分钟时间戳限制
- 公钥可吊销，吊销后该 CA 无法提交
- 题目文件哈希被持久化存储，篡改后可被检测
- 参赛者提交代码哈希被持久化存储
- Runner 拉取参赛者提交时同时获得哈希值，并在执行前校验
- 所有通信使用 TLS
- 企业的评测代码始终存储在企业内网，ARY 不接触
- 违规检测结果实时推送至 Jumbotron 大屏
- 违规队伍在马匹视图中被标记为红色 + DQ
- 违规队伍排名被移除，其他队伍递补
- 频繁时间戳超时的队伍被标记为黄色「高风险」
