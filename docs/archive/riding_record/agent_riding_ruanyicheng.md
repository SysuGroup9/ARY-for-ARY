# Agent Riding Record 阮依成

## 1. 任务背景

作为 ARY GRS 001 项目的产品负责人，需要完成产品需求文档（PRD）的定义，核心命题是：**在 Race 数据存留于 Organizer 侧、ARY 不持久化 Race 数据的前提下，ARY 如何完成赛事的创建、披露、组织与展示？**

**本次任务中遇到的最大困难：**

ARY 不能保留企业的测试代码与其他私密数据，导致评价参赛者变得困难。企业测试代码不能给 ARY，那 ARY 怎么处理企业评分？

**解决方案（自行设计）：**

1. **企业私有 Runner**：主动从 ARY 拉取参赛者代码，在自己的安全环境中评分，测试代码不离开企业内网
2. **赛中测试**：参赛者可主动点击测试，Runner 即时回传结果
3. **进度榜单**：ARY 按规定颗粒度自动读取参赛者最新提交，展示进度排名
4. **赛后最终榜单**：企业综合评分后发布

这个方案解决了核心矛盾：**ARY 不做具体评分，只做中转**，既保证了企业测试代码的安全，又让参赛者能获得反馈。

## 2. 真实对话记录亮点

### 2.1 关于安全核心的讨论（认知演变过程）

**第一阶段：错误理解（以为参赛者值钱）**

**用户**：
> “还有几个有关安全的重要的点需要实现，注意第一周的重点是安全：
> 1、企业的测试数据可能要保密，不能给参赛者
> 2、参赛者的代码属于知识产权，不应该被企业看到
> 3、企业也不应该看到参赛者和 Agent 的对话，只能看到最后的 exe 可执行文件以及排名。”

**Agent**：
> “你说得非常对！这三个安全点是**第一周的核心**，我之前完全没有体现。
> 核心原则：
> - 参赛者可以看到：任务描述、自己的代码和对话
> - 企业可以看到：排名、exe可执行文件
> - 企业不可以看到：参赛者代码、对话记录”

**第二阶段：纠正（参赛者不值钱）**

**用户**：
> “参赛者组内通讯就是采用 DC，默认 DC 是有接口导出代码和对话上下文的。**参赛者的安全部分无需考虑，不值钱！**”

**Agent**：
> “明白了！核心纠正是：**参赛者的安全部分无需考虑，不值钱**。之前把重点放错了，第一周的核心应该是**企业测试代码的安全**，而不是参赛者数据。”

**第三阶段：最终确认**

**用户**：
> “确认下企业给的训练数据是在taskDesc里吗，因为有些比赛还是要有训练数据的。而且我又想到有些比赛有训练数据，有些比赛没有，这应该也是作为企业一个设置的可选项，然后如果有训练数据的那肯定是要给用户的，只是测试的数据要保密”

**Agent**：
> “你说得对！需要区分**训练数据**和**测试数据**：
> - 训练数据：参赛者可见，用于调试
> - 测试数据：仅企业可见，用于评分”

### 2.2 关于去中心化架构

**用户**：
> “老师要求企业发的测试代码，包括之前提到的关键词json文件，ARY不应长时间保留，及其牵引出的评分问题，我们打算采用 runner pull from ARY runner 主动来 ARY 拉取待评测提交。企业侧不需要暴露公网接收口，连接方向更安全，也更容易控审计。”

**Agent**：
> “好的，这个架构调整很重要。核心变化是：**评测不在ARY本地执行，而是由企业私有Runner主动拉取并回传结果，ARY只做中转和展示。**”

### 2.3 关于产品定位纠偏

**用户**：
> “我们假设 ARY 不负责、Agent接管、代码导出由 Dev Compass（以下简称DC）提供。注意：ARY需要负责组内协作功能，只不过一般通过DC完成，而且非本次任务重心。理论上我们只做ARY，DC可有可无，老师提供给我们是可以方便协同合作、点评复盘功能等。而且我觉得ARY应该包含DC。不应该给DC太多的权重，我们可以先假设没有DC这个东西，但保留对合作功能的定义，自定义接口，等后面任务真正要做对应功能时，再把DC容纳进来。老师昨天说不要太依靠DC”

**Agent**：
> “好的，根据你的要求修改：1. 删除第12章‘后续优化方向’ 2. 修正产品定位：ARY需要负责组内协作功能，DC不是必须的 3. 修正系统关系：ARY包含DC，不分开谈，降低DC权重”

### 2.4 关于评分模型

**用户**：
> “这部分不太对，为了安全，现在是让企业自己负责评分，是直接返回给我们一个分数的”

**Agent**：
> “你说得对！企业自己负责评分，直接返回分数给ARY，不需要在PRD里写评分公式。修改后：企业可自定义评价标准，由企业自己的Runner进行评分。ARY不关心企业如何评分，只接收企业Runner回传的最终分数。”

### 2.5 关于赛后展示

**用户**：
> “完整排名公不公开对企业没啥影响，直接就公开了，然后企业可以决定展示前几名的亮点，不一定就是前3名，只是默认”

**Agent**：
> “明白了，修正以下两点：1. 完整排名直接公开，不作为企业可选项 2. 企业可决定展示前几名亮点（不固定3名，企业可设置数字，默认3）”

### 2.6 关于数据保存期限

**用户**：
> “我想问一下，现在主流的这些比赛平台有类似15天后自动清理参赛者代码和Riding记录吗，有的话一般是多少天”

**Agent**：
> “查了一下，主流竞赛平台确实没有统一的15天清理规则。Codeforces、LeetCode、AtCoder等头部平台都永久保存代码。既然主流平台都是永久保留，建议你们：删除15天自动清理的规定（这反而显得不专业），改为永久保存。”

**用户**：
> “那就删除15天自动清理的规定，这部分改回去，也不用特意强调永久保存”

**Agent**：
> “好的，删除15天自动清理规定，也不特别强调永久保存，回归正常描述。”

### 2.7 关于 README 修正

**用户**：

## 3. 认知转变总结

| 阶段 | 错误理解 | 正确理解 | 来源 |
|------|----------|----------|------|
| 第一阶段 | 参赛者代码值钱，企业不能看 | 参赛者不值钱 | 用户纠正 |
| 第二阶段 | 用户数据安全是重点 | 企业测试代码安全是第一重点 | 用户纠正 |
| 第三阶段 | 训练数据和测试数据混为一谈 | 训练数据可见，测试数据保密 | 用户明确 |
| 第四阶段 | 评分公式由平台定 | 企业自己评分，ARY只收分数 | 用户纠正 |
| 第五阶段 | 15天清理数据 | 可保存 | 用户查证后决策 |
| 第六阶段 | 完整排名作为可选项 | 直接公开 | 用户明确 |

## 4. 人机协作模式

- **Agent 负责**：信息检索、初稿生成、方案建议、代码补全
- **人工负责**：需求判断、方向决策、错误识别、内容修正、最终验收
- **协作特点**：Agent 提供建议，人工根据老师要求和实际情况做最终判断。用户多次纠正 Agent 的错误理解。
