## 2. 主要贡献概述

### 2.1 技术架构与实现方案收敛

我在项目中的核心任务，是把“ARY 只负责赛事编排与展示、私有评测逻辑放在 Organizer 侧”的想法，整理成一个能解释清楚、也能逐步实现的技术方案。

这一部分的关键贡献包括：

- 明确系统边界：ARY 不直接承载企业私有测试代码、评分脚本与敏感业务数据。
- 推动 `runner pull from ARY` 这类更符合安全边界的链路表达，使企业侧无需暴露额外公网接收接口。
- 将系统拆分为公开展示层、平台控制层、企业私有评测层，减少“平台既存数据又做私有评分”的边界混乱。
- 在实现层面推动把“用户提交”和“评测任务”区分开，避免提交记录直接兼任完整评测状态机。
- 围绕赛中评分、进度榜单、赛后展示三条主链路，推动形成从提交、入队、拉取、回传、投影展示的整体闭环。

我理解这部分工作的价值，不只是“提出一个想法”，而是把抽象需求往可落地结构上收：哪些数据该长期保存，哪些数据只能临时中转，哪些结果能公开展示，哪些能力必须保留在 Organizer 环境中完成。这是整个项目能够自洽的前提。

### 2.2 PoC 与 Demo 落地推进

在实现层面，我主要关注的是：让系统具备一条真实可跑通的主链，而不是只有静态页面或文档说明。

我重点参与和主导的落地方向包括：

- 赛事创建、报名、提交、评测、榜单、赛后展示这一条主流程的技术落地思路。
- Runner 相关接口链路的整理，包括待评测任务拉取、评测结果回传、公开结果写回等接口语义。
- 对“提交内容临时中转”和“公开结果长期投影”进行区分，尽量贴近项目希望表达的去中心化赛事平台思路。
- 结合排序题、私有 Runner、手动发榜等场景，推动 Demo 具备可演示的最小闭环。
- 关注前端页面与后端 service 的衔接，确保不是单点功能可用，而是完整流程可串起来。

在课程项目语境下，我认为 Demo 的价值在于：老师或评审看到的不应只是功能点罗列，而是一个明确体现“业务边界 + 运行链路 + 可验证结果”的系统原型。因此我在实现推进时，比较强调“能不能跑”“链路是不是闭环”“数据边界有没有讲清楚”。

### 2.3 测试、验证与问题修正

除了实现本身，我还承担了较多“把方案校对成能交付状态”的工作，也就是测试、验证、修正和收尾。

具体包括：

- 检查当前实现与 PRD 之间的对应关系，识别哪些点已经实现、哪些点存在偏差、哪些点只是概念存在但没有真实落地。
- 关注榜单更新、提交频率限制、数据删除时机、赛后展示开关等细节是否与文档表述一致。
- 对 Runner 主链的输入输出契约、任务状态变化、失败场景进行核对，减少“接口能调但语义不清”的问题。
- 关注项目的可运行性，包括本地启动、数据 seed、测试脚本、演示流程是否真实可复现。
- 对一些容易在答辩或验收中被追问的点提前做边界澄清，例如：ARY 是否长期保存原始提交、榜单是否自动更新、Harness 评价由谁产生等。

我认为这类工作虽然不像“新增一个功能”那样显眼，但它直接决定项目最后交上去时是否经得起问答。很多课程项目的问题不是“完全没做”，而是“说法和实现对不上”。我在这一块的作用，是尽量把这种断裂补起来。

### 2.4 文档与技术表达整理

为了让项目成果更容易被老师、队友和后续读者理解，我也投入了较多精力在文档表达与技术说明上。

我的文档类贡献主要体现在：

- 用工程化语言解释系统边界，而不是只从产品描述层面讲故事。
- 帮助梳理实现现状与目标架构之间的关系，说明哪些是当前 PoC，哪些是长期目标。
- 把复杂的实现链路拆成更容易理解的阶段，例如提交阶段、评测阶段、榜单阶段、赛后展示阶段。
- 强调“设计取舍（trade-off）”的表达，例如 PoC 可以接受临时中转，但目标态应尽量减少平台接触原始提交数据。
- 让文档不仅描述“想做什么”，也描述“现在真实做到了什么”。

这部分工作的意义在于：项目文档不是代码的附属物，而是课程评审和团队协作的重要交付。如果没有清晰的技术说明，很多实现价值其实无法被看见。

## 3. 我负责内容的典型特征

如果用更凝练的方式概括，我负责的工作有几个比较稳定的特征：

- **偏技术主线**：更多聚焦系统结构、服务边界、接口链路、数据流转。
- **偏闭环导向**：不是单看一个页面或一个函数，而是看整条功能链是否可运行。
- **偏工程约束**：会考虑安全边界、数据保存范围、任务状态、失败处理和后续维护性。
- **偏验证视角**：不仅要“能做”，还要“能说明”“能演示”“能回答为什么这样做”。

从团队协作角度看，我的工作更像是把产品想法、实现代码、演示流程和技术文档四者往一起对齐，尽量减少彼此之间的偏差。

## 4. 个人反思

这次项目让我更明确地认识到：课程项目里最难的部分，往往不是单点编码，而是**在需求变化、实现限制与展示目标之间做收敛**。

我在这个过程中最大的收获有三点：

1. 需要先把系统边界讲清楚，再谈实现细节，否则会在后期不断返工。
2. PoC 阶段允许折中，但必须把折中写明白，不能把“临时方案”包装成“最终架构”。
3. 技术负责人除了写代码，还要承担解释设计、校对实现、推进闭环和辅助答辩表达的职责。

如果后续继续完善这个项目，我会优先推进三件事：

- 进一步收紧 ARY 与 Organizer 私有数据之间的边界。
- 继续完善 runner 任务模型与结果回传契约。
- 让文档、页面行为和真实实现保持更严格的一致性。
